### T2 Single-table queries (25%, `single_table.sql`)

- [ ] **artist: roster profile with tenure and payout** `R2.0 R2.a` (phase 2, `t2-artist`)  
  Single-row functions: DATEDIFF for days since joining, CONCAT/UPPER for the display line, ROUND(payout_rate * 1000, 2) for payout per 1,000 qualifying plays.
- [ ] **track: newest releases in the catalogue** `R2.0 R2.c R2.d` (phase 2, `t2-track`)  
  ORDER BY release_date DESC with LIMIT N, duration shown as mm:ss. This is the 'new uploads' shelf the business plan says is as findable as a hit.
- [ ] **genre: reference list with a description fallback** `R2.0 R2.e` (phase 2, `t2-genre`)  
  IFNULL on the optional description. A 10-row lookup table risks looking trivial (G3), so give it a business reason, e.g. the label set every probability distribution is spread over.
- [ ] **listener: accounts by plan tier** `R2.0 R2.b` (phase 2, `t2-listener`)  
  COUNT, MIN(signup_date) and average tenure, GROUP BY plan_tier. This is the subscriber mix behind revenue.
- [ ] **scoring_model: deployed model leaderboard** `R2.0 R2.c` (phase 2, `t2-model`)  
  Rank model versions by holdout_accuracy and compare concat vs gated fusion. This shows which model a new station should default to.
- [ ] **station: classify each ambiguity window** `R2.0 R2.e` (phase 2, `t2-station`)  
  CASE on (maximum_ambiguity - minimum_ambiguity) gives narrow, mid or wide. This is how adventurous each listener's station is.
- [ ] **track_score: ambiguity summary per scoring model** `R2.0 R2.b` (phase 2, `t2-score`)  
  AVG(posterior_entropy), MAX(model_divergence) and COUNT per model_id. Included so every table other than the two pure link tables gets its own query.
- [ ] **play: royalty and completion ledger** `R2.0 R2.b R2.e` (phase 2, `t2-play`)  
  SUM(royalty_amount), completion rate, and saved vs skipped counts via IF/CASE, per track or month. Included so every table other than the two pure link tables gets its own query.
- [ ] **Assemble single_table.sql and check coverage** `R2.f R2.0` (phase 2, `t2-file`)  
  One query per non-associative table, 8 in all: artist, track, genre, listener, scoring_model, station, track_score, play. Requirements (a) to (e) must each appear at least once.

### T3 Multiple-table queries (25%, `multiple_table.sql`)

- [ ] **INNER JOIN: each station's genre recipe** `R3.1` (phase 2, `t3-inner`)  
  station INNER JOIN station_blend INNER JOIN genre, ordered by weight. Station Blend is a pure link table: two foreign keys and a weight. Alternative: track_score + genre_probability + genre.
- [ ] **LEFT OUTER JOIN: catalogue with no plays yet** `R3.2` (phase 2, `t3-left`)  
  track LEFT JOIN play (with artist). Finds tracks never streamed, which is the artist-exposure gap. The sample has 4. Alternatives: scoring_model LEFT JOIN track_score (1 unused model), listener LEFT JOIN station (1 listener with no station).
- [ ] **Set operation: tracks saved but never skipped** `R3.3` (phase 2, `t3-set`)  
  Saved EXCEPT skipped. EXCEPT needs MySQL 8.0.31 or later, so this waits on g-version. If the grader's version is older or unknown, use a UNION form instead (e.g. tracks surfaced by a station UNION tracks played without one).
- [ ] **Subquery with a multi-row operator** `R3.4` (phase 2, `t3-sub`)  
  IN, ANY, ALL or EXISTS over a multi-row subquery. Example: tracks whose posterior entropy is above ALL scores in another genre, or listeners who played any track IN a given station's blend.
- [ ] **WITH: artist royalty totals against the platform mean** `R3.5` (phase 2, `t3-with`)  
  A CTE sums royalty_amount per artist; the outer query compares each artist with the average and ranks them.
- [ ] **Assemble multiple_table.sql** `R3.6` (phase 2, `t3-file`)  
  The five queries in order, each with its purpose comment.

### T4 Routines (25%, `routines.sql`)

- [ ] **Function fn_royalty(track_id, seconds_played)** `R4.1` (phase 2, `t4-royalty`)  
  Returns the artist's payout_rate if 30 or more seconds were played, otherwise 0. This is integrity rule I7 from the requirements analysis.
- [ ] **Procedure sp_record_play(...)** `R4.1` (phase 2, `t4-record`)

## Q&A

**Q (2026-10-26):** What has to be done first, before the project can move forward? Is this project almost entirely built upon writing .sql scripts? Is there any additional front-end work to do?

**What has to happen first:** `database_implementation.sql`. The other three scripts all run against the loaded database, so nothing can be written or tested until it exists. It's close: the schema and the 401 inserts already exist and load cleanly. What's left:

1. Generate the merged script from `build_ddl.py`, with a purpose comment before each CREATE TABLE and INSERT.
2. Get it loading on a MySQL 8 you and Nidhi both use (local server or Workbench), so you're testing on the same thing.
3. Settle two small things now, because they shape the later scripts:
   - **Who writes what.** Task 1 needs no split. Once it loads, Tasks 2, 3 and 4 can run in parallel, one person per script.
   - **The grader's MySQL version.** It decides whether the set-operation query can use EXCEPT, which needs 8.0.31 or later.

After that the work fans out. The test harness belongs early too: it's what tells you each script still runs from a fresh database.

**Is it all SQL?** Yes. The graded deliverables are four `.sql` files in a zip, and the brief asks for no front end. The grade rests on two things:

- whether each query meets its requirement;
- whether it's justified by the business plan and is non-trivial.

The second is where points are actually at risk, so that's where the time should go.

**Front-end work:** none is required. The only optional work is showing the finished scripts on the Project 2 site, the way Project 1 showed its deliverables: each query with its purpose comment and the result it returns on the sample data. It earns no points, so it's only worth doing after the scripts are done, and it's cheap at that point because the harness already produces the results.
