## 1. The standard all four .sql files now follow

| Rule | What it means |
|---|---|
| RA claims are true | Anything cited as `(RA: ...)` is actually in the RA. A rule the RA does not state is labelled business policy or a design choice. Every quoted RA phrase is word for word. |
| Branches are accounted for | Every CASE/IF branch fires on the sample data, or the header names it as a guard reached only by the tests. |
| Slide claims are checked | Each header's Class notes lists **Course material** (which unit each construct comes from) and **Beyond the slides** (what is not in any slide, and why it is used). |
| One header layout | Same four sections in every file (FYI, How to Run, NERD STUFF, Class notes). NERD STUFF lists the per-statement comment fields; Class notes ends with a **Branches:** line. |
| One comment format | Every statement has a tagged, structured comment with `Use cases:`, `Business need:`, bullets and `Requirements:`, plus the file-specific fields. |
| Line endings | All four files use CRLF. |

The use cases (UC-xx) stay in the comments. They are not in the RA; they are the team's test design, and the tests are
built from them (`project2/data/use_cases.json`).
